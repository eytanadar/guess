1 Why networks?

Software is built from parts that depend on each other: modules import modules, functions call functions, services call services, packages require packages. Most architecture questions are network questions:

  • What depends on what, and in which direction?
  • Are there cycles, and are they dangerous?
  • If I change this module, what could break?
  • Which parts does everything rely on, and which are safe to change?
  • Is the code organised the way its folders say it is?

This book assumes the Kitchen for loading, querying and drawing. It analyses Python code, which GUESS can read without running it. The same recipes work on any dependency graph you can export, for example as DOT from tools for other languages. Its data are in the cookbooks’ data folder:

file what it is
networkx-imports.gdf The module import graph of the networkx package, version 3.7: 288 modules and 784 import links (importer → imported).
guess-imports.gdf GUESS’s own Python package: 42 modules and 106 import links, a snapshot taken while writing this book.

Both were made with makeFromImports (first recipe). They’re snapshots so that the numbers in this book stay true. Run the command on the installed packages to see their current state.

2 Getting code in

2.1 Read a package’s import graph Basic

You have a Python package (installed, or a folder of source). You want its modules and who imports whom.

Ingredients: an installed package or a source folder · makeFromImports

makeFromImports("networkx")
sizeBy(lines, 3, 30)
dotLayout()

How it works. makeFromImports(target) parses every .py file of a package (by name, such as "networkx", or a folder or file path) without running it. It makes a node per module and an edge from each module to each module of the same package it imports. Nodes get module (the dotted name), package (the parent package), depth, lines, functions and classes. Edges get weight (the number of import statements) and toplevel (false when the import happens only inside a function, a deferred import). level=2 merges modules into their subpackages for a bird’s-eye view, external=true adds the outside packages imported, and tests=true includes test modules. In the browser, the packages GUESS ships with (networkx, numpy, igraph) and GUESS itself ("guess") can be read the same way.

Variations. For other languages, most ecosystems have a tool that writes the dependency graph as DOT, and makeFromDOT opens it. Function call graphs come from makeFromCalls (Call graphs, below).

3 Structure

3.1 Draw the layers Basic

makeFromGDF("guess-imports.gdf")
labelBy(label)
g.nodes.labelpos = "inside"
fitNodesToLabels()
dotLayout()
colorBy(generation, lightgray, purple)

How it works. Laid out top to bottom with dotLayout(), an import graph shows the system’s layers: modules at the top import, and modules at the bottom are imported. generation is each module’s topological level, from 0 for modules nothing imports (here only the package itself) downwards. Cycles are broken for the layout, and the edges that close them point upwards. In GUESS, the data model (model) and the colour table (colors) are at the bottom, imported by nearly everything, and the session at the top ties the parts together.

3.2 Which modules does everything depend on? Basic

makeFromGDF("guess-imports.gdf")
addNodeField("instability", DOUBLE, 0)
for n in g.nodes:
    ca, ce = n.indegree, n.outdegree
    n.instability = ce / (ca + ce) if ca + ce else 0
for n in sortBy(indegree)[-5:]: print(n.module, n.indegree, n.outdegree, round(n.instability, 2))

How it works. indegree counts the modules that import a module (its afferent coupling, in Robert Martin’s terms) and outdegree the modules it imports (efferent coupling). Martin’s instability is outdegree ÷ (indegree + outdegree). Near 0, a module is depended on but depends on little: it’s hard to change (everything relies on it) but has little reason to change. Near 1, a module depends on others but nothing depends on it, so it’s easy to change. Healthy code points dependencies towards stable modules. guess.model is imported by 33 of GUESS’s 42 modules, and its instability is close to 0, as a data model’s should be.

4 Cycles

4.1 Find the import cycles Intermediate

makeFromGDF("guess-imports.gdf")
cycles = [grp for grp in groupBy(strongcomponent) if len(grp) > 1]
[sorted(n.module for n in grp) for grp in cycles]
for grp in cycles:
    for e in (grp <-> grp): print(e.node1.module, "->", e.node2.module, "deferred" if not e.toplevel else "")

How it works. strongcomponent groups modules that can reach each other by following imports: every group of two or more is a cycle (two modules that import each other, or a longer loop). Python tolerates an import cycle when at least one import in it runs late, inside a function, after both modules have loaded. A cycle of only top-level imports can fail at start-up depending on which module is imported first. GUESS has three two-module cycles (algorithms–igr, model–states and styles–visuals). In each, at least one direction is deferred, so all three are safe. feedbackEdges() lists a small set of edges whose removal would break every cycle: the places to refactor first.

5 Change impact

5.1 What could a change break? Basic

You want to know, before changing a module, which other modules could be affected.

makeFromGDF("guess-imports.gdf")
affected = ancestors(guess_model)
affected.color = red
guess_model.color = orange
len(affected), len(g.nodes)

How it works. An edge runs from importer to imported, so the modules that can be affected by a change to model are its ancestors: everything that imports it, directly or through others. Here that’s 34 of 42 modules. Change it carefully and test widely. descendants(m) goes the other way: everything m needs, which is what you must ship or mock to test it alone.

5.2 Who controls access to whom? Advanced

makeFromGDF("guess-imports.gdf")
dominatorTree(guess_session)
sorted(set(n.idom for n in g.nodes if n.idom))

How it works. In the graph reached from session, a module’s immediate dominator (idom) is the last module that every import path from session to it must pass through. Modules that dominate others are gatekeepers. Here most modules are dominated by session itself (it imports them directly), and a few are reached only through commands, colors, geo or glyphs. That’s a map of which modules load which, useful when deciding what to load lazily.

6 Organisation

6.1 Does the code follow its folders? Intermediate

makeFromGDF("networkx-imports.gdf")
remove(module == "networkx")
leidenClusters()
compareClusters(leiden_class, package)
colorize(leiden_class)

How it works. The folders (packages) are the intended structure, and the communities of the import graph are the actual one: groups of modules that import each other more than they import the rest. compareClusters scores the agreement (1 = identical). For networkx it’s about 0.65: broadly organised by folder, with algorithms that lean on other folders’ helpers. Look at the modules whose community differs from their folder. They’re often misplaced, or a sign that two folders are really one.

Pitfalls. The package root distorts everything. Nearly every networkx module does import networkx as nx, which links each module to the root, so the first step is remove(module == "networkx"). The same happens in any package whose __init__.py re-exports its contents.

6.2 A package-level view Basic

makeFromImports("networkx", level=2)
labelBy(module)
sizeBy(lines, 10, 60)
circoLayout()

How it works. level=2 merges every module into its two-level parent (networkx.algorithms.flow.maxflow becomes networkx.algorithms), giving a dozen subpackages and the imports between them: the architecture diagram a newcomer needs, drawn from the code rather than from memory.

7 Call graphs

7.1 Map who calls whom in a module Intermediate

makeFromCalls("guess.structure")
sizeBy(indegree, 6, 30)
colorize(public)
labelBy(function)
forceAtlas2Layout()
unused = [n.function for n in g.nodes if n.indegree == 0 and not n.public]
unused

How it works. makeFromCalls(module) makes a node per function and method, and an edge for each call it can resolve by name: f(), self.f(), Class.f(). Nodes get function, cls, lines, params and public (no leading underscore). The most-called functions are the module’s helpers. Private functions that nothing in the module calls are candidates for dead code. Here there are three: _constraint, _effsize and _generation. None of them is dead. They compute the constraint, effsize and generation fields, and they’re listed in a table of computed fields rather than called. So before deleting a function, check that it isn’t used from outside (grep), registered in a table or as a callback, or called through a variable.

Pitfalls. Matching by name is an approximation. Calls through variables, to other modules or by dynamic dispatch are missed, and two functions with the same name in different classes can be confused. Treat the graph as a map for reading code, not a proof.

8 Case studies

8.1 Case study: the cycle hidden in import networkx as nx Intermediate

makeFromGDF("networkx-imports.gdf")
len(feedbackEdges()), len(strongcomponent.distinct)
root = (module == "networkx")
root[0].indegree
remove(root)
recompute()
len(feedbackEdges())
max(groupBy(strongcomponent), key=len)

At first sight networkx is riddled with cycles: feedbackEdges() lists 260 edges to break. Nearly all of them pass through the package root. Its __init__.py imports the subpackages so that users can write nx.shortest_path, and 253 modules import the root back. Remove the root and recompute, and only 9 cycle-closing edges remain. Most sit in one knot of seven modules inside networkx.utils, which provides the decorators and backend dispatching that the rest of the library builds on. The pattern is typical of convenient top-level APIs. It’s harmless at run time, because Python finishes loading the root before the submodules use it, but it hides the real structure from naive analysis. Remove the facade before you read the architecture.

8.2 Case study: GUESS, read by GUESS Basic

makeFromGDF("guess-imports.gdf")
sizeBy(lines, 8, 50)
colorBy(indegree, lightgray, red)
labelBy(label)
dotLayout()
sortBy(lines)[-3:]

The book’s last recipe is the program reading itself. GUESS’s largest modules are layouts (the layout algorithms), model (graphs, nodes, edges and fields) and session (the console and the protocol to the page). Colour by indegree and the foundation is plain: model and colors are imported by most of the system, and each command module (structure, analysis, geo, builders…) is imported only by the session, which installs it. That’s the shape you want: new commands, like the ones added for these cookbooks, can be written without touching anything that depends on them.
